## What changed

**One `@spfn/core` under `spfn dev`.** A project without `"type": "module"` — every `spfn create`
scaffold — ran its server source as CommonJS under `tsx` in development, and `tsx` loaded a
second copy of each `@spfn/*` package beside the server's own. The app configured one copy and the
server ran the other. Rate-limit policies and trusted proxy hops did not reach `@spfn/auth`'s
routes, and with a required second factor an account without one got 403 on the very routes that
enrol one, so it was locked out (issue #329). Production builds were not affected. `spfn dev` now
runs server source as ESM, as `spfn build` does, and a server process refuses a second copy of
`@spfn/core`, naming the file that loaded it.

**One route map, whichever command writes it.** `spfn dev`'s watcher generated the committed route
map under `development`, while `spfn codegen run` and `spfn build` generated it under
`production`, so the file depended on which command ran last. Code generation now always runs
under `production`. A router whose generated file would differ under `development` or `test` is
refused, whether the difference is a route, a `.csrf()` declaration, the order of the routes or a
mounted package router.

**MCP routes load without the app origin.** `@spfn/mcp` accepts `appUrl` as a function, called at
the first request instead of when the router is created. An app that mounts the MCP route and
passes `appUrl` as a function can run `spfn codegen run` without `SPFN_APP_URL` set; an app that
passes a string read from the environment behaves as before. A new `resourcePath` option names
the resource's path in code.

**Passkey-only sign-in can be closed.** `@spfn/auth` has a `passkeyLogin` channel. An app whose rule
is a password plus a passkey sets `channels: { passkeyLogin: false }`, and the passkey sign-in
routes answer 404. It is on by default.

**Security floors.** The packages require Next.js `^16.4.5`, `hono` `^4.13.16` and
`@hono/node-server` `^2.1.6`, and the AWS and Google Cloud SDKs they accept have floors whose
lowest versions reach no known advisory. The [CHANGELOG](../../CHANGELOG.md) lists each range.

## What can break, and who must act

- **Everyone:** 0.3 and 0.4 packages cannot be mixed. Upgrade every `@spfn/*` package and `spfn`
  together.
- **Apps run with `spfn dev` without `"type": "module"`:** CommonJS in server source —
  `require`, `__dirname`, a named import from a `module.exports` file, a CommonJS file that
  requires `@spfn/*` — no longer runs in development. All but the named import already failed in
  production.
  The [CLI README](../../packages/cli/README.md#your-server-source-runs-as-esm-as-it-does-in-production)
  tables each case.
- **Apps on an older `spfn` CLI:** the new `@spfn/core` refuses to start under it.
- **Apps with `tsx` below 4.22.4:** raise it; older releases print a deprecation warning on
  Node 26.
- **Apps on Next.js below 16.4.5, or installing the KMS, SNS, SES or Cloud Storage SDKs
  themselves:** raise them.
- **Routers that register routes, CSRF or mounts by environment:** code generation refuses them.
  Register them unconditionally and branch inside the handler.
- **Committed generated files:** regenerate once. The `Generated with NODE_ENV` header line is
  gone.
- **`NODE_ENV=development spfn build`:** `next build` and the server build now run under
  `production`.
- **`@spfn/auth` with a required second factor and two copies of `hono`:** the server refuses to
  start instead of answering 403.
