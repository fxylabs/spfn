02
Core technique

The server can't
mint a token.

Most auth stacks sign tokens with a server-held secret — whoever holds that secret can mint any user's token, and one leak compromises every session. @spfn/auth inverts the direction: each client generates its own ES256/RS256 keypair, registers the public key at login, and signs its request JWTs locally. The server only verifies, against the stored public key the JWT's keyId points to. There is no signing secret on the server to steal, logout is just revoking a key, and keys expire after 90 days with rotation built in. Native social sign-in follows the same rule — the server verifies the provider's id_token, binds it to the client's public key, and still never issues a token itself.

03
What's inside

The parts you'd otherwise
build again.

client-signed JWT

Asymmetric ES256/RS256 — devices hold keys, the server verifies.
oauth

Pluggable provider registry — Google, Apple, GitHub, Kakao, Naver built in.
sessions & guards

Cookie sessions for Next.js — RequireAuth, RequireRole, getSession, opt-in session binding.
rbac

Runtime roles and permissions, seeded at boot, checked per route.
otp & one-time tokens

Email verification codes and single-use tokens.
registration gate

beforeRegister hook — invite-only, allowlists, custom checks.
admin seeding

Declarative admin accounts, created at lifecycle boot.
deletion & recovery

Grace-period account deletion with a recovery window.
second factor

TOTP or a passkey, plus recovery codes — asked only of accounts that enrolled.
device link

A signed-in device shows a code; a new phone or browser reads it and signs in.
ops tokens

Scoped, revocable tokens that spfn ops commands answer to.
mcp authorization

OAuth 2.1 server, so Claude Code and Codex connect to /mcp as the user.
